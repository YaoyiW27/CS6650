● Bug Found: Race Condition in postAlbumCount

  I found the bug! It's a classic race condition in the postAlbumCount function.

  The Problem (main.go:129-130)

  current := albumCounts[index].Count
  albumCounts[index].Count = current + 1

  This code spawns 10,000 goroutines that all try to increment the same counter
  without synchronization. The read-modify-write operation is not atomic,
  causing lost updates.

  Evidence from CloudWatch Logs

  The logs clearly show the race condition in action:

  Request 1: Final Count: 10000  ✓ (correct)
  Request 2: Final Count: 19994  ✗ (expected 20000, lost 6 increments)
  Request 3: Final Count: 29987  ✗ (expected 30000, lost 13 increments)
  Request 4: Final Count: 39987  ✗ (expected 40000, lost 13 increments)
  Request 5: Final Count: 49974  ✗ (expected 50000, lost 26 increments)
  Request 6: Final Count: 59974  ✗ (expected 60000, lost 26 increments)
  Request 7: Final Count: 69974  ✗ (expected 70000, lost 26 increments)
  Request 8: Final Count: 79973  ✗ (expected 80000, lost 27 increments)
  Request 9: Final Count: 89958  ✗ (expected 90000, lost 42 increments)

  Each request should add exactly 10,000 to the counter, but due to the race
  condition, many increments are lost when multiple goroutines read the same
  value simultaneously and overwrite each other's updates.

  The Fix

  The fix would require synchronization using either:
  - A sync.Mutex to protect the counter
  - atomic.AddInt64() for atomic increments
  - A channel-based approach
